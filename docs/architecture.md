# hcflow Architecture

## Decision Record: Language Choice

**Decision: Go**

| Criterion | Go | Python | Node.js |
|-----------|----|----|---|
| Single binary | ✅ | ❌ | ❌ |
| Cross-platform | ✅ | Partial | Partial |
| Embedded HTTP server | ✅ | ✅ | ✅ |
| subprocess execution | ✅ | ✅ | ✅ |
| YAML/JSON | ✅ | ✅ | ✅ |
| Startup time | Fast | Slow | Medium |
| Distribution | Binary | venv/pip | npm |
| No runtime dependency | ✅ | ❌ | ❌ |

Go was chosen because:
- Single binary distribution (no runtime to install)
- Fast startup (CLI tools run on every save/status check)
- Embedded HTTP server for `hcflow ui`
- Strong subprocess/OS integration

## Layered Architecture

```
┌─────────────────────────────────────────────────┐
│                   User Interface                 │
│         CLI (cobra)       Web UI (HTTP)         │
└────────────────┬───────────────┬────────────────┘
                 │               │
         ┌───────▼───────────────▼───────┐
         │         Service Layer          │
         │  status  doctor  release  pr  │
         └───────┬───────────────┬───────┘
                 │               │
     ┌───────────▼───┐   ┌───────▼───────────┐
     │  Git Service  │   │  GitHub Service   │
     │  (git CLI)    │   │  (gh CLI)         │
     └───────────────┘   └───────────────────┘
                                │
                     ┌──────────▼──────────┐
                     │  External Systems   │
                     │  GitHub API         │
                     │  GitHub Actions     │
                     │  Release Please     │
                     └─────────────────────┘
```

## Source of Truth Principle

hcflow does **not** maintain its own database. All state lives in:

| State | Source of Truth |
|-------|----------------|
| Branch/commits | Git |
| PRs / CI status | GitHub API (via `gh`) |
| Versions / tags / releases | Release Please + GitHub |
| Configuration | `.hcflow.yml` |
| Workflows | `.github/workflows/hcflow-*.yml` |

## Service Boundaries

### `internal/config`
Reads/writes `.hcflow.yml`. Schema versioning. No external calls.

### `internal/git`
Thin wrapper around the `git` CLI. All git operations go through here.
**Mockable via interface** for testing without a real git repo.

### `internal/github`
Thin wrapper around the `gh` CLI. All GitHub operations go through here.
Returns structured types parsed from `gh`'s JSON output.
**Mockable via interface** for testing without a GitHub account.

### `internal/status`
Aggregates state from `git` and `github` into a single `State` struct.
No external calls itself — composes the services.

### `internal/doctor`
Runs diagnostics against the environment. Reads but never writes.

### `internal/migrations`
Versioned schema migrations. Each migration is:
- Explicit (described in code)
- Idempotent (safe to run twice)
- Tested

### `internal/web`
Embedded HTTP server with static files (HTML/CSS/JS) bundled via Go's `embed`.
Exposes `/api/status` which calls the same services as the CLI.

## CLI and UI share the same core

```
         hcflow core (services)
        /                       \
  CLI (cobra)              Web UI (HTTP)
  hcflow status            /api/status
  hcflow release           pipeline view
  hcflow doctor            repo info
```

No business logic is duplicated between CLI and UI. The web handler calls
the same `status.Gather()` function used by `hcflow status`.

## Workflow Architecture

Workflows generated by `hcflow init` are minimal wrappers:

**Consumer repo** (`.github/workflows/hcflow-ci.yml`):
```yaml
- name: Run CI commands
  run: |
    make lint
    make test
```

The commands come directly from `.hcflow.yml`. No DSL, no plugin system.

## Schema Versioning

`.hcflow.yml` carries an explicit `schema:` field.

```yaml
schema: 1
```

When the schema advances:
1. A new `Migration` struct is registered in `internal/migrations`
2. `hcflow upgrade` applies it
3. `hcflow doctor` warns if schema is outdated

Migrations are never destructive without explicit user confirmation.

## Security Model

- `hcflow ui` binds to `127.0.0.1` only (never `0.0.0.0`)
- No secrets are stored or printed
- GitHub tokens are managed entirely by `gh auth`
- Workflows use minimal permissions (`contents: read`, etc.)
- Destructive git operations (`--force`, `--hard`) are never executed automatically
